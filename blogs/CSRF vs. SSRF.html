CSRF vs. SSRF: Same Four Letters, Completely Different Attacks

Dhanusha K · Sept 26, 2026 · 8 min read

Every so often someone in a report review meeting says "wait, is this the CSRF one or the SSRF one?" It's a fair mix-up - the acronyms are one letter apart, they both get thrown around in the same "web app vulnerabilities" breath, and both have "forgery" energy to them. But that's genuinely where the similarity ends. Once you look at who's doing the forging and where the request is actually going, they're not even in the same neighborhood.

Let's untangle them properly.

The One-Sentence Version First
CSRF: the victim's browser is tricked into sending a request it didn't mean to send.
SSRF: the server is tricked into sending a request it shouldn't be able to send.

That's really the whole difference. Everything else is detail. But let's get into the detail, because the detail is where the good findings live.

CSRF: Weaponizing the Victim's Own Browser

CSRF (Cross-Site Request Forgery) abuses one simple fact: browsers attach cookies to requests automatically, regardless of which site technically triggered the request. If a victim is logged into bank.com and then visits a malicious page, that malicious page can quietly fire off a request to bank.com - and the browser, being helpful, tags along the victim's session cookie without asking anyone's permission.

What it actually looks like:

<!-- Sitting on attacker-site.com, waiting for a logged-in victim to visit -->
        <form action="https://bank.com/transfer" method="POST" id="f">
          <input type="hidden" name="to" value="attacker-account">
          <input type="hidden" name="amount" value="5000">
        </form>
        <script>document.getElementById('f').submit();</script>

The victim clicks a link, this fires silently, and if bank.com isn't checking for a CSRF token or verifying the request's origin, the transfer just... happens. The victim's browser did all the talking. The server has no way to tell "the user clicked a button on our actual site" apart from "some other page made the browser do this," because the cookie looks identical either way.

The core weakness: the server trusts the session cookie as proof of intent, without verifying that the request actually originated from a legitimate action on the legitimate site.

How you test for it: strip out or tamper with the CSRF token in a sensitive request (password change, fund transfer, email update), replay it, and see if the server still processes it. If yes - and there's no other origin-verification happening - you've got CSRF.

SSRF: Weaponizing the Server's Ability to Make Requests

SSRF (Server-Side Request Forgery) is a completely different animal. Here, there's no victim browser involved at all. Instead, you find a feature where the server itself makes outbound HTTP requests based on user-supplied input - a "fetch image from URL," a webhook setup, a PDF-generator that loads a URL, a URL preview feature, anything like that - and you abuse it to make the server request somewhere it was never meant to reach.

What it actually looks like:

POST /api/fetch-avatar
{
        "image_url": "http://169.254.169.254/latest/meta-data/iam/security-credentials/"
}

That IP - 169.254.169.254 - isn't random. It's the cloud metadata endpoint (AWS, and similar addresses exist for Azure/GCP), and it's only reachable from inside the server's own network. Your browser can never reach it. But if the server-side code blindly fetches whatever URL you hand it, you've just turned the application's own backend into your personal proxy into its internal network - potentially walking out with cloud credentials, hitting internal admin panels, or scanning internal infrastructure that's normally firewalled off from the outside world entirely.

The core weakness: the server trusts user-supplied URLs/hostnames as safe destinations to fetch, without restricting what internal or unexpected destinations that request could actually reach.

How you test for it: find any feature that takes a URL as input and causes server-side fetching, then point it at internal IP ranges (127.0.0.1, 169.254.169.254, 10.x.x.x, 192.168.x.x), a Burp Collaborator/interactsh listener to confirm out-of-band interaction, and see what comes back or what callback you catch.

Putting Them Side by Side

The real "aha" moment is this: CSRF makes someone else's browser attack a server on the victim's behalf. SSRF makes the server attack itself (or its internal network) on the attacker's behalf. The forgery in CSRF happens in the victim's browser. The forgery in SSRF happens inside the server's own request logic. Nobody's browser needs to be tricked for SSRF to work - the attacker talks directly to the vulnerable endpoint.

One more thing that trips people up: CSRF needs a victim. No victim visits the malicious page, no attack happens. SSRF needs no victim at all - you, the attacker, interact with the vulnerable server directly and it does the dirty work itself. That's honestly the fastest way to mentally sort the two when you're staring at a finding and blanking on which is which.

Why Mixing These Up in a Report Is a Bad Day

Get this wrong in a write-up and you'll send a dev team looking for a CSRF token when the actual bug is unrestricted server-side URL fetching, or vice versa - and the fix couldn't be more different:

  • CSRF gets fixed with anti-CSRF tokens, SameSite cookie attributes, and origin/referer validation.
  • SSRF gets fixed with strict allowlisting of destinations the server is permitted to fetch, blocking requests to internal/private IP ranges, and disabling unnecessary URL-fetching features entirely where possible.

Tell a team to "add a CSRF token" for an SSRF finding and they'll add a token that does absolutely nothing to stop the server from still reaching 169.254.169.254 on request. The bug survives the "fix."

The Takeaway

Don't let the acronym similarity fool you into treating these as siblings - they're not. CSRF is about borrowing a victim's trusted identity through their browser. SSRF is about borrowing the server's trusted network position. Different attacker, different victim, different mechanism, different fix. The only thing they genuinely share is a name that's one swapped letter away from causing a very avoidable mix-up in your next report.
