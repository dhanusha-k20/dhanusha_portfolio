Reflected XSS vs. DOM-Based XSS: Why They Trip Up Even Experienced Testers

Dhanusha K · Sept 5, 2026 · 8 min read

If you've spent any time doing web app VAPT, you've probably had this moment: you find an XSS, you go to classify it, and you pause. Is this reflected, or is this DOM-based? On the surface, they look almost identical - a payload goes in, a script executes, an alert box pops up. But under the hood, they're completely different animals, and mixing them up in a report is the kind of thing that gets flagged in a technical review.

Let's break down why they look the same, and how to actually tell them apart.

Why They Feel So Similar

Both vulnerabilities:

  • Are triggered by attacker-controlled input (usually a URL parameter)
  • Result in JavaScript execution in the victim's browser
  • Are typically delivered via a crafted link sent to the victim
  • Show up in your proof-of-concept the exact same way:<script>alert(document.cookie)</script> popping a box

If you're just eyeballing the PoC, both look like "I put a script tag in the URL and it ran." That's exactly why testers new to the space (and honestly, some experienced ones on a rushed engagement) lump them together. The difference isn't in what you see - it's in how the payload actually gets executed.

Reflected XSS: The Server Is Involved

In reflected XSS, your payload takes a round trip through the server. You send a request, the server takes your input, embeds it directly into the HTML response without sanitizing it, and sends that back to the browser. The browser just renders whatever it's told - it has no idea it's rendering something malicious.

Example flow:

Request: GET /search?q=<script>alert(1)</script>
          Server:  "You searched for: <script>alert(1)</script>" ← reflected straight into the HTML
          Browser: Parses the HTML, sees a <script> tag, executes it

The key tell: if you view-source or check the raw HTTP response, your payload is sitting right there in the server's response. The server processed it and reflected it back.

DOM-Based XSS: The Server Is Never Involved

DOM-based XSS never touches the server at all. The vulnerability lives entirely in client-side JavaScript that reads data from somewhere (usually location.href, document.URL, document.referrer, or the URL fragment after a #) and writes it into the page using something dangerous like innerHTML, document.write(), or eval() - without sanitizing it first.

Example flow:

URL:     https://example.com/page#name=<img src=x onerror=alert(1)>
          Server:  Never sees the fragment after # - it's not even sent in the HTTP request
          JS:      var name = location.hash.substring(6); document.getElementById('greeting').innerHTML = "Hello, " + name;
          Browser: JS pulls the payload straight from the URL and injects it into the DOM

The key tell: if you check the raw HTTP response from the server, your payload is nowhere in it. The server literally never saw it. Everything happened client-side, in the browser, after the page loaded.

The Quick Mental Model

Reflected XSSDOM-Based XSS
Who processes the payloadServerClient-side JavaScript
Where's the payload in the response?Present in the raw HTTP responseAbsent from the raw HTTP response
Common sourceURL query parameterslocation.hash, location.search, document.referrer read via JS
Common sinkServer-side template embedding input into HTMLinnerHTML, document.write, eval, setTimeout with a string
Where you'd find the bugServer-side code / template renderingClient-side JS files (view-source, JS debugger)

How to Actually Tell Them Apart While Testing

This is the part that matters in practice - a repeatable check, not a guess:

  1. Send your payload, then view the raw HTTP response (Burp's response tab, not the rendered page). If your exact payload is sitting in the response body, it's reflected.
  2. it's not in the response, but the script still executes - open dev tools, check the Sources/Debugger tab, and trace where the DOM is being modified. Look for innerHTML, document.write, eval, or similar sinks reading from location.hash / location.search.
  3. Fragment-only payloads (#) are a strong DOM-based signal - anything after # in a URL never gets sent to the server in the first place, so if execution still happens, it has to be client-side JS doing the work.
  4. Check the JS source directly. With DOM XSS, grep the page's JS for location.hash, location.search, document.URL, or document.referrer feeding into innerHTML/eval/document.write. That's your source-to-sink chain, and it's what you'll actually put in your report.

Why the Distinction Actually Matters in a Report

It's not just pedantry - the remediation is different:

  • Reflected XSSgets fixed server-side: proper output encoding/escaping wherever user input is embedded into HTML (context-aware encoding, not a blanket filter).
  • DOM-based XSSgets fixed client-side: safe DOM APIs (textContent instead of innerHTML), sanitization libraries like DOMPurify before any dynamic HTML insertion, and avoiding eval/document.write on untrusted data entirely.

If you tell a dev team to "fix the server-side encoding" for a bug that's actually happening in client-side JS, they'll patch the wrong layer, retest will still fail, and you'll be the one explaining why.

The One-Line Takeaway

Reflected XSS = the server hands the browser a booby-trapped page.
DOM-based XSS = the browser builds the booby trap itself, from data the server never even saw.

Same explosion, different wiring.
