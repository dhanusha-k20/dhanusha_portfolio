Session Fixation vs. Session Replay: Two Ways an Old Session ID Can Ruin Your Day

Dhanusha K · Sept 12, 2026 · 5 min read

Picture this: you're testing a login flow, you grab a session token before authentication, and somehow that same token is still valid after the user logs in. Bug found - but which bug is it? This is one of those pairs that gets flagged interchangeably in draft reports until someone asks "wait, is this fixation or replay?" and the room goes quiet for a second.

They're not the same vulnerability. They're not even really testing the same weakness. But they both revolve around one idea - the application isn't treating session IDs as something that should die and be reborn at the right moments - so it's easy to see how the lines blur.

Start With What They Actually Have in Common

Both bugs involve a session token that outlives the moment it should have expired. Both let an attacker end up in control of, or riding along on, a session that belongs to someone else. And in both cases, your proof-of-concept ends the same way: two browser tabs, one session ID, one very awkward "wait, I'm logged in as the victim now" moment.

That shared ending is exactly why they get confused. The difference is entirely in how you got there.

Session Fixation: You Hand the Victim a Trap Before They Even Log In

This one starts before authentication. The attacker sets or obtains a valid, pre-authentication session ID and tricks the victim into using it - usually by sending a link with the session token baked into the URL, or by planting it via a cookie if the app allows that.

The critical flaw: the application doesn't issue a new session ID after the victim logs in. It just takes the pre-existing session, silently upgrades it to an authenticated one, and carries on. The attacker, who already knew that session ID from the start, now shares an authenticated session with the victim without ever having to steal anything mid-flight.

How you actually confirm it in testing:

  1. Grab a session ID/cookie before logging in (an unauthenticated session).
  2. Log in normally using that same session.
  3. Check whether the session ID changed post-authentication.
  4. If it's identical pre- and post-login, you have fixation - the attacker's session ID silently became a valid, authenticated one.

It's fundamentally a bug in session ID lifecycle management at the login boundary.

Session Replay: You Reuse a Session That Should Already Be Dead

Replay is a different story entirely. There's no "planting" involved - the attacker simply captures a session ID that was valid at some point (via network sniffing, a stored request, a proxy log, browser history, whatever) and reuses it later, after the point where it should have been invalidated.

The critical flaw here: the server doesn't actually kill the session when it should - after logout, after a password change, after a defined expiry window, or after the user closes the browser without an explicit logout. The session ID technically still works because the backend never bothered to invalidate it server-side.

How you actually confirm it in testing:

  1. Capture a valid, authenticated session ID (e.g., from a Burp history entry or proxy log).
  2. Perform the action that should kill it - log out, wait past the stated timeout, change the password.
  3. Replay the old request using the captured session ID.
  4. If the server still honors it and serves an authenticated response, that session was never actually invalidated. That's replay.

It's fundamentally a bug in session termination and expiry enforcement, not the login boundary at all.

The Distinction That Actually Matters When You're Testing

Ask yourself one question and the confusion mostly disappears:

Did the session ID exist before login and get reused across the authentication boundary (fixation)? Or did a session that was already authenticated get reused after it should have expired or been killed (replay)?

Fixation is about the moment of login. Replay is about the moment of termination. Same "old token still works" symptom, opposite ends of the session's lifecycle.

One more practical tell: fixation usually requires the attacker to interact with the victim beforehand (send them a link, plant a cookie) - there's a social engineering step. Replay just requires the attacker to have seen a valid session ID at some point; no interaction with the victim is needed at all, which is part of why it's the one people tend to underestimate in impact.

Why Your Report Needs to Get This Right

Same story as always - the fix is different depending on which one you found:

  • Fixation gets fixed by regenerating the session ID at the moment of authentication, every single time, regardless of whether a session already existed.
  • Replay gets fixed by properly invalidating sessions server-side on logout, enforcing real expiry windows, and ideally binding sessions to something like IP/user-agent context so a stolen token is harder to reuse cleanly.

Recommend "regenerate session ID on login" for a replay bug and the dev team will patch a boundary that was never the actual problem - the old session will still be sitting there, perfectly valid, waiting to be replayed.

Bottom Line

Fixation: the attacker gives the victim a session ID before login, and it survives into an authenticated state.
Replay: the attacker reuses a session ID after it should have expired or been killed, and the server doesn't check.

Different bug, different fix, same underlying lesson - session IDs need a clear birth and a clear death, and most of these vulnerabilities are just the app fumbling one or the other.
